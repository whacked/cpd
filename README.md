# yayamdb (cpd)

yet another yamlish database

say you are compiling a list of korean words you'd like to study.
you start with a text file where every line looks like
hangul,meaning
고양이,猫
사슴,鹿

then you think you should add a column for the TOPIK level of the vocabulary
hangul,meaning,level
고양이,猫,1
사슴,鹿,2

but then you realize that a word included in the TOPIK 1 vocabulary must also be in TOPIK 2

# objectives

1. human friendly plain-text format (implies linediff-friendly)
2. jsonschema-based schema declarations and validation
3. 100% reversible sqlite export/import

# assumptions

- the database is simple
- a human will interact with the data using a text editor
- consumers can append records to the database by appending lines to the end
- records may have unspecified fields

## how to deal with unspecified fields

for fields that appear only once, we will assume they are special cases and leave them alone.
for fields that appear more than once, we will assume they can be treated as columns.

# yaml structure:

```yaml
_schemas:
table1: jsonschema of table1
table_2: jsonschema of table_2
tableThree: jsonschema of tableThree

_keys:
table1:
table_2: jsonschema of table_2
tableThree: jsonschema of tableThree

_codecs:


table1:
table_2:
tableThree:
```

## schemas as CUE (shorthand)

Instead of writing JSON Schema by hand, a `_schemas` entry may be a **CUE block
scalar** (requires the `-tags cue` build). It is compiled to JSON Schema before
validation. The outermost braces are optional — a CUE block scalar is implicitly
a top-level struct — so write fields directly:

```yaml
_schemas:
  data...: |
    status: "ok" | "fail" | "warn" | null
    name:   string
    temperature?: number | null
```

`name?:` marks an optional field, `A | B` is an enum, `... | null` allows null,
and `[...string]` is an array. The `data...:` suffix means "this describes one
record; wrap it as an array." Braces are needed in only one place: a struct
nested inside an array keeps them (`[...{...}]`). See `cpd --examples` for the
full reference.

# design considerations

## use case

several independent collection devices with asynchronous sync or no automatic syncing at all.
thus you end up with several flat files.

does it make sense to combine all of them into one giant file?
if you combine them into one giant file, sqlite as an endpoint would seem a lot more attractive.
but going sqlite early means if you want to schemafy, you'd end up doing a lot of table adjustments.

so it's probably better to keep many separate small files, and provide utilities to cross inspect / validate the separate schemas among different files

### jsonl-to-cpd

Convert flat JSONL with enum-like fields to CPD YAML. The 'status' column is auto-promoted to a join table.

**Input** (`cpd basic.jsonl`):

```jsonl
{"name":"alpha-1","temperature":22.5,"status":"ok"}
{"name":"alpha-2","temperature":23.0,"status":"ok"}
{"name":"beta-1","status":"fail","temperature":19.8}
{"temperature":20.0,"name":"beta-2","status":"warn"}
{"status":"ok","temperature":21.0,"name":"gamma-1"}
{"name":"gamma-2","temperature":null,"status":"fail"}
{"name":"delta-1","temperature":18.4,"status":"warn"}
{"name":"epsilon-1","temperature":17.0,"status":"unknown"}
{"name":"zeta-1","temperature":22.0,"status":null}
{"name":"eta-1","temperature":25.0}
```

**Output** (`yaml`):

```yaml
_columns: [status, payload]
status:
  ok: 1
  fail: 2
  warn: 3
  unknown: 4
data:
  - [1, {name: "alpha-1", temperature: 22.5}]
  - [1, {name: "alpha-2", temperature: 23.0}]
  - [2, {name: "beta-1", temperature: 19.8}]
  - [3, {temperature: 20.0, name: "beta-2"}]
  - [1, {temperature: 21.0, name: "gamma-1"}]
  - [2, {name: "gamma-2", temperature: null}]
  - [3, {name: "delta-1", temperature: 18.4}]
  - [4, {name: "epsilon-1", temperature: 17.0}]
  - [~, {name: "zeta-1", temperature: 22.0}]
  - [~, {name: "eta-1", temperature: 25.0}]
```

### cpd-to-jsonl

Expand a compacted CPD YAML (positional arrays + join tables) back to full JSONL.

**Input** (`cpd compacted.cpd.yaml`):

```yaml
_schemas:
  data:
    type: array
    items:
      type: object
      properties:
        status:
          type: [string, "null"]
        time:
          type: number
        comment:
          type: string
      required: [time]
_columns:
- status
- time
- comment
status:
  on: 1
  off: 2
  standby: 3
  error: 4
data:
  - [1, 1, "system initialized"]
  - [2, 2, "manual shutdown"]
  - [1, 3, "auto-restart triggered"]
  - [3, 4, "awaiting input"]
  - [2, 5, "manual shutdown"]
  - [4, 6, "fault code 17"]
  - [1, 7, "system idle"]
  - [2, 8, "scheduled cycle"]
```
